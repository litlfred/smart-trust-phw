Security — one question, asked at every boundary

Skill security: The security sub-KG’s entry point. What the boundaries are, which machinery already guards each one, and the single rule that unifies them — refuse, never repair. Read this before adding a check, so the answer that already exists is reused rather than rebuilt in a fourth place.

Named by: Publishing the docs site, and keeping the previews alive

This value came from outside. What may I do with it?

Everything in this package is that question at a different boundary. The split is not by attack name: the same untrusted string is command injection at a shell, path traversal at a join, and XSS at a template, and filing the rule under each name is how a correct guard ends up in one file while other call sites hand-roll it.

The rule that unifies them: refuse, never repair

A check returns a refusal, not a cleaned-up value. A repair silently changes which artefact is named: a slug pipeline that replaces disallowed characters can turn a branch of --- into the empty string, so rm -rf "pages/branches/$SLUG" names every preview. A refusal makes the caller decide, and only the caller knows whether that is a 400, an exit 1, or a skip.

And check by VALUE, never by provenance. Re-run a guard after the value crosses a job boundary (feature-staging.yml does): “where it came from” is not a property you can read off a variable.

Where to look when adding a check

  1. Is the boundary in the table? Then the machinery exists — extend it. Adding a second guard for a guarded boundary is how they drift apart.
  2. Is there already a helper? src/core/safe-path.ts is the path one. A correct helper in one file does not protect call sites that hand-roll the check.
  3. Can a gate hold the property? A hand-maintained invariant drifts, and the symptom of forgetting is invisible. A guard without a gate is a guard with an expiry date.

What this package does NOT own

Shell rm -rf is not where the open surface is. The staging deletion sites are guarded by value; the surface that needed this package is the TypeScript I/O layer.

Deletion policy is not security. Whether an agent may remove a durable artefact at all is deletion-requires-confirmation, and it governs cases where the path is perfectly safe and the deletion is still wrong.
